# Structured documentation

Flavor: minimal. Precedent: kohle's documentation sweep (`~/code/kohle`,
`dev/specs/cli-documentation.md`, `dev/design/cli-documentation.md`, issues
090–106). Where this document and that precedent differ, this document wins.

## Overview

Harald's docs already render as a strict MkDocs site, but nothing in them is
checked. Every `harald-cli` line sits in an `sh` or `text` fence, the key
tables are hand-written, and the README repeats the feature list and carries a
second roadmap that already disagrees with `docs/roadmap.md`. The developer
notes sit in the user site, and nothing is published. A renamed command,
changed output or rebound key goes unnoticed until someone reads the page.
This sweep builds the machinery that keeps the docs honest:

- a short README
- a user guide published to GitHub Pages
- checked `console` examples
- a generated CLI reference
- TUI key tables verified against the code
- a local-only developer site
- a demo GIF
- docs rules in `AGENTS.md`

Rewriting the content of the study and getting-started pages is a separate,
later step.

**Timing.** Implementation is paused for about a week while the user uses the
app and gathers user-facing review points. This brief, its spec and its issues
go ahead in the meantime.

## Goals

- **README.** It holds only:
  - the pitch (the existing "reading, TV and conversation" line stays)
  - a short taste, which is a checked `console` block (e.g. `lookup lief`,
    `lookup --en use`)
  - a link to the guide
  - how to read the guide locally
  - the licence and data note

  The feature list moves into the guide. The README keeps the one roadmap,
  which follows the briefs in `dev/inbox/`. `docs/roadmap.md` is removed and
  nothing links to it.
- **User guide.**
  - `docs/` is built strictly. A broken link, a broken anchor, or a page on
    disk but missing from the nav fails the build.
  - It is published to GitHub Pages from `main`, and only after a strict build
    succeeds. A failed build publishes nothing.
  - Pull requests build it but do not publish it.
- **Developer site.** `docs/developer/*` moves to a local-only site in
  `dev/docs/` with its own `mkdocs.yml`, also strict. It is never built in CI
  or published, and the user guide's index and nav no longer link to it.
- **Checked examples.** Every ` ```console ` fence in `docs/**/*.md` and in
  `README.md` is a checked example.
  - **Syntax.** `$ ` lines are commands, and the lines under each one are its
    expected output. An optional `<!-- docs: ... -->` comment above a fence
    carries options from a closed vocabulary, with `illustration` among them.
    A module docstring in the checker defines the syntax.
  - **Running.** Examples run in the normal `uv run pytest`, offline, against
    a small sample lexicon built from shipped sample sources, a scratch
    `learning.db` and a scratch config. They never touch the user's real files.
  - **Width and clock.** Output is pinned to 80 columns. Any date or clock
    shown is pinned.
  - **Match.** Output must match exactly, line by line, ignoring trailing
    whitespace.
  - **Problems the checker reports.**
    - an unknown option word
    - a non-`harald-cli` command in a console block
    - a shell operator
    - a command that would prompt
    - any `harald-cli` invocation outside a console fence that is not marked
      `illustration`; the commands that cannot run in a test (`build
      --fetch`, `prune`, the Termux install) are marked this way
  - **Commands are written bare** (`$ harald-cli lookup lief`).
    `getting-started.md` explains `uv run` once, for the desktop.
- **Generated CLI reference.** `docs/reference.md` is generated by mkdocs-click
  from the `harald-cli` Click group. It covers every command, its options, and
  `--config`/`HARALD_CONFIG`. Click help text is the one source for option
  wording, and the hand-written pages explain behaviour rather than list
  options.
- **TUI documentation.**
  - The TUI (Home, lookup, entry, add word, study) is documented in
    hand-written prose and key tables.
  - A test verifies each key table against its screen. A row whose key the
    screen does not handle fails, and so does a visible bound key missing from
    its table.
  - Keys handled by a widget rather than the screen's `BINDINGS` (e.g. `space`
    ticks a row, `enter` submits an input) are allowed and accounted for.
- **Demo GIF.** A VHS recording of the README taste at 80 columns is checked
  in and regenerated by hand. A test fails if the tape's commands differ from
  the README block in text or order. The steps to regenerate it live in
  `dev/docs/`.
- **AGENTS.md gets a `## Documentation` section.** It says that:
  - `docs/` is the user-facing description of behaviour and the README is
    only a pitch that points to it
  - these are the build commands for both sites
  - the checker's docstring defines the example syntax
  - a slice that changes user-visible behaviour updates the matching page in
    the same PR
  - when an example's output changes, the page is fixed, never the example
    loosened
  - the README roadmap follows the inbox briefs
  - the personal-data rule (next item) applies
- **Personal data.** The user's own cards, notes, decks, review history, the
  words they are learning, and their own setup (devices, paths, sync
  arrangements) never appear in user-facing docs. Examples use the sample
  lexicon's words and invented notes. The Termux timing becomes generic:
  "about 11 minutes on a recent phone".
- **No page is exempt.** The machinery covers every page from the start, with
  no lint exemptions. On `docs/user/getting-started.md` and
  `docs/user/study.md` only fences and key-table markup change, and their
  prose waits for the content pass.

## Non-Goals

- Rewriting the content of `getting-started.md` and `study.md`. That is the
  **content pass**, a named later step that waits for the user's review points
  from about a week of use. It is not an issue to start now.
- Screenshots, a GIF or snapshot tests of the TUI.
- Checking examples against the real Wiktionary lexicon.
- Publishing or CI-building the developer site.
- Versioned docs, translations, a custom domain, Sphinx.
- Any change to Harald's behaviour. The only code-adjacent change is help-text
  and docstring wording that the generated reference surfaces.

## Technical Approach

- **Toolchain.**
  - Python 3.12 and uv. MkDocs 1.6 and mkdocs-material 9.5.39, as pinned now
    in `docs/requirements.txt`, plus mkdocs-click.
  - The docs toolchain never enters `pyproject.toml`.
  - The reference imports harald, so both local use and CI run
    `uv run --with-requirements docs/requirements.txt mkdocs ... -f docs/mkdocs.yml`.
    The README's current `pip install` instructions go.
- **Existing setup.**
  - `docs/mkdocs.yml` has `docs_dir: .` and `strict: true`. It still needs the
    nav-omission and anchor validation that kohle added.
  - `admonition` is enabled but unused. A checked fence must not sit inside
    any construct the checker cannot see.
  - `.github/workflows/docs.yml` builds but does not deploy. It gains the
    Pages deploy, gated on `main` and on a successful build.
- **Sample data.** Hand-cut wiktextract-style sources covering the words the
  pages show, built into a sample lexicon once per test session. Whether these
  reuse or extend `tests/fixtures/*.jsonl` or live in `docs/examples/` is the
  architect's call.
- **TUI key check.** Textual `Binding`s are declared on the screens in
  `src/harald/tui/`. How a key table names its screen and how widget keys are
  declared is the architect's call.
- **Order.**
  1. Skeleton: site config, moving the developer pages out, removing the
     roadmap page.
  2. The checker, with its first converted page.
  3. The reference.
  4. The key-table test.
  5. The remaining fence conversions.
  6. The README cut and the GIF.
  7. The AGENTS.md section.
  8. The content pass, later and gated on the review points.

## Open Questions

None for the user. Left to the design: where the sample sources live, the seam
for pinning the clock and the 80-column width, the option vocabulary beyond
`illustration`, and how key tables are bound to screens.
